## 5. 任务 B：摘要要求必须落到实际引用范围

### B1. 建立可信的来源范围表

为三篇现有论文生成独立、版本化的摘要区域表，先从解析块/行与标题边界整理候选，再对照原 PDF 核定摘要起止。记录核定方式及 AI/人工状态，自动建议未经核定不能直接成为可信标签；D8 的答案总体确认不等于确认这张新表。

范围表至少绑定论文 ID、处理版本、PDF SHA、解析/过滤输入哈希，以及原文 segment、块/行、字符范围和文本哈希。chunk 必须按真实来源区间与已核定范围匹配；不是给模型任意填一个 `section=abstract`。

- PDF 第 1 页不自动等于摘要；摘要也不强制只能在第 1 页。
- 关键词、相似度高低、模型自报章节或标准答案命中，不是摘要标签的依据。
- `segment_bbox` 是父片段区域，不能冒充 chunk 的精确边框。
- 未核定、跨摘要/正文的完整 chunk 保守记为 `unknown` / `mixed`，不作为纯摘要引用。D9 不偷偷裁掉正文来制造合格证据。
- 范围表标注的是文档结构，可用于任意问题，不包含题号或答案要点；修改后生成新版本并重新绑定。

计划产物：`artifacts/d9/source_regions.json/.md` 及原 PDF 范围对照材料。SQLite/Qdrant 不新增伪造章节字段，也不重建全部文档向量。

### B2. 从原问题确定来源约束

首版只覆盖明确的摘要限定，例如原问题中的 “in the abstract”“摘要中/摘要提到”。记录中英规则和支持范围，使用原始问题确定约束；改写后的检索查询不能解除它。否定、引用或含糊措辞要有保守规则和离线反例，不能宣称理解了所有自然语言来源要求。

在线路径不能读取 `case_id`、`expected_points`、`expected_evidence`、`answerable` 或评分文件来决定回答、来源范围、补查查询。即使增加显式来源选项，也必须与原问题要求协调，不能用“不限章节”覆盖明确摘要限定。

### B3. 固定 RAG 与 Agent 共用门槛

两模式继续共享同一首轮真实 top-5；保留完整原始召回和 rank，另外记录来源合格候选、实际展示及排除理由。先做来源资格筛选，再按原完整片段/字符预算构建模型证据。不能把“检到了正文但不合格”改写成物理检索 `no_hits`。

| 情况 | 固定 RAG | Agent |
|---|---|---|
| 摘要限定且有合格展示证据 | 从该证据生成并逐条校验 | 从该证据决策；正常最多一次补查规则保留 |
| 首轮没有合格摘要展示证据 | 保持一轮，返回 `insufficient_evidence`，说明本轮来源不足 | 不允许直接回答；在首次正常决策门允许一次补查或不足 |
| Agent 使用补查 | 不适用 | 原摘要约束继续生效；按核定摘要 chunk/point 集合做范围过滤，仍 top-5，不增加检索轮次 |
| 补查仍缺合格展示证据 | 不适用 | 返回不足；没有第三次检索 |
| 范围表/身份/哈希损坏 | `tool_error` | `tool_error`，不能交模型猜测修好 |
| 模型输出来源违规 | 不发布越界答案，按明确输出错误/共享修复规则处理 | 同左；引用修复是终态处理，不能重新开工具 |

范围过滤必须与选定完整论文/版本配对及 profile 同时成立，资格来自已核定文档结构，不能直取某道题的标注 chunk。当前 Searcher 仅支持版本/profile 过滤，D9 必须新增受控来源过滤接口，并核验与原过滤条件的交集、成对首轮适配与补轮透传；不是靠查询中多写 abstract 就算硬过滤。ready 的完整入库计数检查仍按原版本范围验证，不能用摘要子集数量冒充完整 ready 数量。没有合格可检索范围时提前说明不足，不发送明知无效的 embedding 请求。

目前 `context.py` 会丢弃额外来源字段，消息构造又要求证据字段集合严格一致。实施时将范围绑定、资格与排除原因放在明确版本化的外层记录/消息契约中，保持原文快照完整；不要直接往旧证据对象塞字段而绕开验证。

发布前和引用修复后都逐结论检查实际 `citation_ids` 的来源资格。一条正确摘要引用不能掩盖另一条正文引用；初版对摘要限定保守要求每条引用都合格。模型仍只能引用最终实际展示集合中的原文，程序不能拿未展示 PDF 内容替答案补证明。

完成标准：双模式都挡住正文冒充摘要；真实核定摘要可以通过；普通正文题不被误限；旧策略/结果保留；**来源合规仍不等于语义支持，仍需 F 评价。**

## 6. 任务 C：剩余时间要传到实际请求

当前聊天请求已受剩余时间约束，`embed_texts()` 仍使用固定 30 秒。D9 通过可选关键字参数或预算适配器连接检索与 embedding，旧的两参 embedding / 三参检索调用继续可用；不能靠捕获 `TypeError` 后回退重发请求。

1. 采用单调时钟；在 ready 校验后、真实 HTTP 发送前重新计算剩余时间。没有剩余时间就停止，embedding 请求计 0。
2. 请求超时上限取 `min(30 秒, 剩余时间)`；计数以实际 HTTP 发送尝试为准。当前 Searcher 在调用 embedder 前先记 1，新增低层截止检查后须传回 `request_started=false` 等可核对状态，未发 HTTP 的请求/失败次数不能误计 1。已发送请求失败仍计一次，已知 tokens 保留，未知值为 `null`，不自动加 embedding 重试。
3. 对向量返回、Qdrant 查询、SQLite/PDF 核验、生成、修复、关闭资源等阶段补适用的前后检查。A 明确业务终态提交点；提交前任何终态跨 deadline 统一为 `budget_exceeded`，原工具/格式故障保留为 `interrupted_failure` 等诊断，不能仅对正常终态检查。已提交的不可变历史不因后续导出/渲染迟到追溯改写；导出失败按独立故障记录约定保存。
4. 独立固定/Agent 从各自运行开始用同一预算。成对共享首检索也接截止时间；两模式各扣共享首检索实际耗时，不扣另一模式的等待/执行时间；Agent 补查只用当前模式剩余额度。
5. 模拟“首检索耗 119 秒”，两模式开始业务时各约剩 1 秒，不能重新拿到 120 秒。

完成标准：请求前到期时未发送 HTTP、embedding 尝试计 0；已发送后超时或迟到有正确记录；修复/网络重试不重置 deadline；两模式预算公平；新 D9 记录如实标明 embedding 剩余时限已连接。

HTTP 超时通常约束网络阶段，同步本地操作也可能阻塞。因此最终文档继续说明：**已接请求剩余超时和阶段检查；未证明整个进程严格 120 秒强制退出。** 不用无法取消底层调用的线程包装冒充硬中止。
