## 1. 目标和现状

页面只保留一个聊天入口。用户选择论文后直接提问，无需选择固定 RAG 或 Agent；侧栏、回答头部和详情不显示采用的方式，也不增加“自动模式”标签。后台保存实际过程和用量，旧固定 RAG 保留在 CLI／对照实验中。

实施前 Agent 先用完整问题检索，再判断是否补查一次；有历史时的准备调用只补全追问。现在问题理解和检索规划合为一次前置调用：简单问题执行一条实际计划查询，按需最多补查一次；复杂问题按必要信息需求分别查证，轮流合并各查询排名中的完整原文后，一次综合回答原问题。

```text
当前问题 + 近期对话 + 所选论文的现有信息
  → 一次理解与规划
      → 对象不清楚：沿用澄清交互
      → 简单问题：一条实际计划查询 → 原单查询 Agent 流程（按需一次补查）
      → 复杂问题：独立子问题 → 分别检索 → 合并原文 → 一次综合回答
  → 段落正文 + 引用编号 + 既有历史和下载
```

## 3. A：用户不选择内部方式

- 修改 `app.py`，移除问答模式 radio、两模式解释、每轮回答顶部方式 caption，以及详情里的模式行。侧栏和欢迎页只说明选择论文、提问与原文回查。
- 新提交不再读取旧 `question_mode` 状态，统一走现有 `mode="agent"` 交互入口，前置计划由 B 生成并由 C 执行。后台沿用原模式字段和报告格式，不为页面新增 `auto` 模式枚举。
- 历史固定 RAG 报告按原内容展示和下载，页面隐藏其方式标签；不改写历史文件、目录或旧实验结果。
- 沿用即时用户消息、局部加载、新对话、历史切换、上传、引用弹窗和下载。README 的当前操作说明同步更新。

验收重点：新问和追问无模式选择；切回旧固定 RAG 和 Agent 报告也不显示方式；原文回查、下载和页面重绘不再次提交。

## 4. B：一次前置调用，按信息需求拆解

- 在 `conversation.py` 和 `d9_runtime.py` 的现有准备位置接入规划。首问也执行一次；有历史时直接扩展原追问理解调用，不先补全再额外调用分类器和规划器。
- 输入沿用当前问题、近期历史和所选论文／解析版本，补充已有标题及可用摘要背景。复用现有论文信息读取，不新建摘要缓存或元数据哈希；这些信息用于规划，不能自动作为最终答案的引用证据。
- 保留 `user_question`、`standalone_question`、`clarification_question` 和明确回查原文时的 `referenced_evidence_ids`。仅增加 C 实际消费的子查询列表及对应论文范围，保存在本轮报告中。
- 简单事实问题生成一条查询；机制、比较、概览和明确多部分问题按独立信息需求拆解，通常少量子问题即可，不固定拆成五条，也不加段数或子问题数量评分门槛。
- 每条查询结合论文真实主题和术语。例如 Raft 概览可以围绕研究问题、核心机制和贡献／评价取证，避免只生成“方法、贡献、结论”等泛词。跨论文比较按同一维度分别查各论文，不将不同实验条件混成一组事实。
- 原始来源限制从完整问题确定，并沿用到所有子查询。例如“仅根据摘要”不能因子查询没写“摘要”而放宽。每个子查询关联当前已选版本，不检索未选论文。
- 对象不明确时沿用澄清。完整问题已经明确但子查询不可用时回退为该完整问题的单查询，不另开规划修复调用；若整个追问理解未成功、指代尚未明确，则沿用简短澄清／失败兜底，不猜测对象。

验收重点：首问一条或多条查询、明确追问补全后再拆解、歧义先澄清、摘要限制与论文对象保留。B 的离线模拟验证流程，不证明模型拆解的语义质量。

## 5. C：多个查询共享证据，最终回答原问题

- 在现有 Agent 入口消费计划，复用已打开的混合检索器及 rerank。简单问题沿用原一次检索及按需一次补查；复杂问题执行计划中的查询后直接进入现有 `final_decision` 综合一次，首版不叠加事后补查或每个子问题的独立答案生成。
- 每条子查询沿用 top 5，在当前资源中依次执行。记录真实子查询、所查版本、结果及 embedding／重排用量，不先无条件执行一轮完整问题检索再重复所有子查询。
- 实施前的合并函数只支持两轮且要求首轮问题等于完整问题；已增加直接服务于子查询列表的合并接入点，复用来源筛选和上下文选择。原检索记录中的 query 保留实际子问题，不伪装改回完整问题来绕过旧假设。
- 按“各子问题第一条 → 各第二条”的顺序轮流纳入候选，用已有 `chunk_id` 去重；各查询内部保留自身排名，不直接比较不同查询的分数。沿用最终最多 8 条完整证据／8000 字符预算，不新建评分器或哈希。
- 用户明确回查的旧原文按现有关系优先恢复；各子问题命中的锚点随后优先保留，邻近正文只使用剩余额度。必要时调整 `evidence_reading.py` 的排列，使某个主题的相邻片段不会再次挤掉其他主题。
- 各查询的候选统一按完整问题的来源要求筛选。最终 `context.question`、回答与引用检查都使用完整问题；不能因执行最后一个子查询而只回答它。
- 当前初次 Agent 决策只接受 5 条证据，最终决策接受 8 条。复杂问题直接使用最终决策接收合并证据，不硬裁为 5 条，不为该路径扩大旧初次决策规则。
- 一个子查询失败时保存已取得的证据和实际失败用量，最终回答说明对应信息缺口。没有可用答案时沿用现有折叠原文兜底，不发布未完成 JSON 或伪造完整覆盖。
- 在本轮原报告中记录计划、各子查询与检索结果及最终来源；标明计划检索与既有补查，避免把第二条计划查询误记成一次补查。复用 `search_rounds`、用量汇总与 JSON／Markdown 导出，必要时同步 `agent_export.py`，页面不显示内部方式名。

验收重点：多个主题和多篇论文的结果都可进入证据池；最后一条子查询不改变原问题；同一片段被多个子问题命中时只保留一份；摘要限制、旧引用重读和最终引用对应正确；局部失败仍保留已有证据与真实用量。
