## 实际交付

`agent.py` 消费 B 的 `planned_queries`。简单问题使用计划中的实际查询及论文范围，沿用原初次决策和按需一次补查。复杂问题在同一已打开的检索资源中依次执行各条查询，每条 top 5，复用混合检索及重排，然后直接进入既有 `final_decision`。不会先无条件检索完整问题，也不为每个子问题生成独立答案或叠加事后补查。

`agent_context.py` 新增计划合并入口，原始检索记录保留实际子查询、对应论文／解析版本及各自排名。合并按各查询第 1 条、各查询第 2 条依次纳入，以已有 `chunk_id` 去重，不比较不同查询的分数。沿用最多 8 条完整证据和 8000 字符预算，超出预算的片段不截断为可引用原文。简单问题初次决策仍最多 5 条，复杂问题使用支持 8 条的最终决策。

`source_scope.py` 按完整问题的来源要求统一筛选各条查询候选；子查询可以省略“摘要”，仍不能用正文越过摘要限制。每条检索只查其计划指定且已被用户选中的版本。最终上下文的问题、回答消息和引用检查使用完整问题，最后一条查询不会替代用户真正的问题。复用 B 的计划归一化逻辑，没有追加规划修复请求。

用户明确回查的旧原文继续按已有关系优先恢复。复杂计划在 `evidence_reading.py` 先保留合并后的全部锚点，再用剩余额度读取邻近正文，避免一个主题的邻近片段挤掉其他查询的锚点。原单查询和 CLI／实验路径继续使用原行为。

某条计划检索失败时，`search_rounds` 保存实际查询、范围、错误和 embedding／重排用量，其他查询继续执行并保留已取得的证据。最终上下文列出检索失败或没有原文进入最终上下文的查询，已发布回答附带对应缺口说明；失败用量不会算成零，未知 token 不伪装为已知。合并来源的查询编号沿用原计划编号，第一条失败后，第二条成功也不会被改记为第一条。没有可发布答案时继续使用页面已有的折叠原文兜底。

`app.py` 的“来源资格与检索轨迹”展示计划、各条实际查询、论文范围、结果、用量及最终展示来源；计划查询与补查分别标记。`agent_export.py` 在既有 Markdown 中加入相同过程，JSON 继续保存完整本轮报告。第二条计划不会被误称为补查，页面也没有增加方式标签。

## 遇到的问题与取舍

原两轮合并函数要求首轮查询等于完整问题、论文范围也完全相同，不能直接用于子查询。新增入口保留真实检索记录，复用原上下文选择和来源筛选；单条计划补查仍保持原补查优先顺序。

实现时发现 Markdown 只读取 `search.error` 会漏掉没有成功检索结果的失败行，已改为优先读取该行实际错误，局部失败的 runtime 场景确认导出保留错误。浏览器发现计划轨迹还显示“新增召回 ID：未知／新增展示 ID：未知”，已改为仅在原报告具有对应补查字段时展示。页面方法初次 2.535 秒通过；因这次具体页面修改重跑，最终 2.112 秒通过，其他已通过且代码未变的方法直接复用。

本次只接通独立子查询共享原文后综合回答；最终 8 条／8000 字符上限可能仍使某些查询没有可展示原文，此时保留缺口说明。离线模拟证明流程、范围、预算和记录接通，不证明真实模型规划质量或回答准确率提高。没有新增依赖式多跳、通用调度、评分器、校验层、哈希、审计或快照。
