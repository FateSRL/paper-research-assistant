## 1. 实际完成什么

在 [lexical_retrieval.py](/D:/course/paper-research-assistant/paper_assistant/lexical_retrieval.py) 的 `BM25Index` 中，复用 SQLite 选定论文/解析版本的已有 chunks 正文构建本地词项统计，保留原有 chunk ID、PDF 页码与正文。每份 chunk 是一个文档；BM25 依据查询词在片段中出现的频次、词项在选定语料中的稀有程度和片段长度计算分数。参数为 `k1=1.5`、`b=0.75`：高频增加收益会趋缓，长片段会做长度归一化，避免单纯因为篇幅长而占优。

`tokenize()` 将英文词项和数字统一 `casefold()`，中文用连续文本中的相邻双字词项，单个汉字保留为一个词项；不自动翻译查询，不生成模拟答案。论文正文主要为英文时，方法名、缩写和指标名可以直接参与关键词召回，中文宽泛问题仍主要依赖语义路径及 D11 的主题化补查。同一查询重复词项只计一次，只返回具有正词项匹配分数的片段。

统计只来自当前选定论文/版本，不把其他论文版本混进候选。相同版本组合的正文词项处理在同一个 searcher 生命周期内复用；不另写磁盘索引、扫描哈希或维护后台更新任务。摘要限定时按允许的实际 point ID 过滤词项候选，并在该子集内计算文档频率与平均长度，使关键词路径遵守相同来源要求。

实际离线方法在临时 SQLite/Qdrant 和模拟问题向量下确认：BM25 候选参与融合，同一个 searcher 的第二个查询复用本地词项索引，`get_version_chunks()` 总调用一次，每次检索仍仅一次问题向量请求。这里的请求是模拟供应商调用，真实 embedding API 为 0；没有给正文重新生成向量。

## 2. 怎样学习：约 20 分钟

1. 读 `lexical_retrieval.py` 的 `tokenize()` 和 `BM25Index.score()`，分别找出词频、文档频率、平均长度三个量。
2. 对照 [SQLite 原文读取](/D:/course/paper-research-assistant/paper_assistant/storage.py)的 `get_version_chunks()`，说明关键词索引为什么直接复用已有正文及原文定位。
3. 用一句包含 `RAG`、`retrieval` 的英文文本和一句中文解释口头展示分词结果；不需要发起模型调用。
4. 比较只查英文方法名与只用中文泛称的命中条件，再读 D11 的 [补查查询日志](/D:/course/paper-research-assistant/docs/v1/d11/d11-B-retry-query-guide.md)。

## 3. 关键问题与答案

**BM25 为什么可能补上向量漏掉的正文？** 向量按照整体语义相似度排序，BM25 按实际词项匹配排序。精确的方法名、缩写或指标名可能在语义排序中靠后，却在关键词路径中靠前。两路是否提高本项目最终回答效果，要看保存答案和原文支持，不能由算法名直接推断。

**有了 BM25，还需要向量检索吗？** 需要。同义表达、语言差异和概述问题可能缺少相同词项，单用 BM25 会漏掉相关正文。D13 保留语义路径，由 RRF 融合两路名次。

**中文 bigram 能把中文问题和英文论文匹配起来吗？** 不能自动完成跨语言翻译。它提供中文文本的本地词项处理；英文正文匹配需要查询中的英文词项，或由向量语义路径召回。D11 已有的补查决策可以结合标题和论文语言生成英文主题查询。
