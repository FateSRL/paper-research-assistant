## 1. 当前基础与目标

规划时 `app.py` 已保存并展示历次问答，但提交时只把当前问题、所选版本和模式传给 `d9_runtime.run_question()`，后端没有收到对话历史；该缺口现由 A、B 补齐。页面原有逐轮独立报告、逐句引用弹窗及 JSON／Markdown 下载；弹窗从被点击回答的 `answer.evidence_sources` 读取原文，其 key 已含提交标识。这套回查关系直接复用。

本阶段完成以下行为：

- 同一组论文内可以追问“它的停止条件是什么”“解释刚才第二条结论”“把上一条回答说简单一点”。
- 有足够上下文时补全问题；存在多个合理指代对象时先澄清，用户回答后继续。
- 回查显示该轮用户问题、补全后的完整问题、结论、论文版本、PDF 页序和实际引用原文；之后继续聊天或切换论文不会改变旧答案的来源。
- 聊天历史帮助理解意图，论文事实仍由本轮实际提供的原文支持。

流程：

```text
当前问题 + 同会话近期历史
  → 无历史：沿用单轮入口
  → 有历史：最多一次追问补全
      → 对象不明确：返回澄清问题，等待用户下一次输入
      → 对象明确：形成完整问题
          → 现有混合检索与重排
          → 固定 RAG／一次补查 Agent
          → 现有引用校验
          → 保存该轮答案并展示原文引用
```

### A：会话生命周期

- 复用现有提交记录，加 `conversation_id`，以所选 `(paper_id, parse_revision)` 集合绑定会话。论文选择顺序变化不新建会话；集合或版本变化时开启新会话。
- 保留旧回答供回看。旧记录没有会话字段时仍按现有方式显示和下载。
- 初始历史窗口取最近 3 个完整交互轮次，并设置 4000 Python 字符的历史输入上限；历史内容包括用户问题、逐条简短回答及最近的澄清问答，不把全文证据和技术轨迹塞进聊天历史。超限优先移除较早轮次；可用历史不足以确定指代时走澄清。
- 历史中的结论保留轮次、结论顺序和依据类别，便于理解“刚才第二条”；工具故障不当作知识回答。提交时固定历史，页面重绘不重新选取或重跑同一提交。
- 第一版只支持当前页面会话；跨刷新／重启恢复、历史摘要和长期记忆暂不纳入。

### B：追问、原问题和证据

- 无历史时不增加模型调用。有历史时，通过共用 `RecordedLLM` 最多一次准备调用，输出完整问题或澄清问题；复用现有结构化输出的必要解析，不增加独立分类器、置信度门槛或专用校验框架。
- 保存 `user_question` 和 `standalone_question`，不丢失用户原始输入。完整问题补充明确的对象、实验和来源要求，不把历史模型推断写成已证实的论文事实。
- `rag.py`、`agent.py` 的问题参数、来源范围判断和 `context.question` 必须一致，不能只改外层检索字符串。回答消息另外携带原始追问和有限历史，支持“说简单一点”等表达要求；无会话字段的旧调用沿用原行为。
- 新增会话层的 `needs_clarification` 结果，携带 `clarification_question`；本轮停止在检索前，保存已发生的聊天用量，不生成论文答案或引用。页面与既有导出按澄清交互展示，问答核心的五种终态继续沿用。用户下一次回复在同一会话中结合澄清问题重新理解。
- 回答中的论文事实尽量写清主体和条件。`paper_evidence`、`model_knowledge`、`analysis` 仍按 D12 规则分开，历史回答不自动成为论文依据。
- 若追问明确针对上一轮原文，按相关引用 ID 从当前所选版本取回真实片段，纳入本轮 `shown_evidence` 和已有上下文预算，再使用现有引用校验。历史中的 ID 本身不授予本轮引用资格。
- 准备调用失败按实际工具、格式或预算错误返回；不继续使用含糊追问猜测对象，不另开准备修复循环。

### C：回查与记录

- 原有 `run_id`、提交标识、逐条结论和 `evidence_sources` 已足以关联该轮答案。补充会话关联和问题信息，不建立第二套来源存储。
- 用户输入位置显示原问题；回答详情及引用弹窗提供本轮完整问题，让用户能核对系统是否理解了正确对象。确认过对象后，正文明确写出方法／实验名称。
- 引用仍从被点击的该轮报告读取固定论文版本、原文和 PDF 页序；引用编号在该轮内有效，不能用当前最新回答或当前侧边栏选择替换旧引用。
- 复用已有原文展示。需要解释原文中的代词时，通过现有正文读取提供实际上下文；章节归属证据仍不足时据实说明，不将聊天主题补成原文来源。
- 正常回答和澄清交互的新增字段由既有页面、记录及导出消费者接通。保留旧报告兼容；本阶段不增加全会话导出或新的回查产品。

## 3. 调用预算与接入位置

每轮继续使用同一个 `ChatBudget`：最多 3 次聊天尝试、总时限 120 秒；追问补全、回答、补查后的回答、网络重试和既有修复共享这些额度。

| 路径 | 正常聊天调用数 | 剩余额度 |
|---|---|---|
| 首问，无历史 | 固定 RAG 1 次；Agent 直接回答 1 次，补查后回答 2 次 | 沿用现有额度 |
| 追问补全后直接回答 | 补全 1 次 + 回答 1 次 | 最多余 1 次供既有修复／重试 |
| 追问补全后 Agent 补查 | 补全 1 次 + 首轮决定 1 次 + 补查后回答 1 次 | 已满，不追加第四次调用 |
| 对象不明确 | 准备调用返回澄清，正常 1 次 | 停止本轮；用户回复后是新的交互轮次 |

已有检索轮数、重排调用、最终最多 8 条／8000 字符证据上限继续沿用。历史文本另有小窗口，不能挤占或冒充真实论文证据。查看引用、重绘和下载不发模型请求。

预计接入现有 `app.py`、`paper_assistant/d9_runtime.py`、`context.py`、`agent_prompt.py`、`rag.py`、`agent.py` 和既有记录／导出路径；必要的会话准备逻辑可以放在一个小模块中。实施时按实际调用链改动，不为拟修改文件清单建立锁定、清单哈希或新绑定机制。现有 CLI、开发对照和 D14 单轮验收不传历史时保持单轮流程。
