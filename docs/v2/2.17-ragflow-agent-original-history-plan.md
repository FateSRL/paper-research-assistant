## 3. 新工作流程与消息组织

### 3.1 保留现有 Agent 取证与临时事实准备

```text
用户原问题
    ↓
现有 search／read_context → 当前预算内的原文窗口
    ↓
临时事实准备：facts／answerable／missing_information
    ├─ 核心缺口且可继续取证 → 现有工具循环 → 再准备
    └─ 可以回答、无可靠取证方向或达到原有限额
              ↓
       延续本次成功准备请求的消息历史
       ＋本次准备响应＋最终作答指令
              ↓
       一次最终生成 → 原有引用／来源处理 → 展示与保存
```

五次自主决策、五次 `search/read_context` 共用取证额度、原问题、选定版本、来源范围、补证分流及通用知识直接回答能力沿用现有规则。准备仍计入自主步，最终阶段不提供工具，不增加评审、重写或第二个答案候选。

### 3.2 从实际成功准备请求接到最终请求

最小接法是复用最终所消费的那次成功 `prepare_answer` 对应的实际消息和响应，不从所有 `action_steps` 逐份拼接请求：

```text
system：本次最终生成的有效规则
原准备请求的非 system 消息：已有工具调用／结果、原问题、实际原文窗口
assistant：本次成功准备响应
user：现在基于上述原文和准备结果生成完整答案；本阶段只允许 answer
```

- 原准备 system 被最终 system 替换，避免同时要求 `prepare_answer` 和 `answer`。历史中的旧动作合同属于前一阶段，当前阶段由最后的指令明确接管。
- 原文保留在实际准备请求已有的 `evidence_sections` 中；不在最终 payload 再复制一套相同正文，也不让模型再次摘录原文。
- 新准备响应作为一条 assistant 消息追加，最终指令不再重复塞入整份相同事实包。必要的原问题、输出要求、来源限制、引用 ID、当前缺口仍明确可用。
- 如果准备不足后经过失败／重复工具调用，最终消费保存的准备时，应使用与该准备绑定的实际请求、原文 context 和响应，不能错取最后一次工具调用。若新原文到达并重新准备，则使用新的成功准备。
- 准备发生格式修复时，采用成功解析那一次对应的请求和响应；最终格式／引用修复继续保有同一批原文。保留原有共享修复额度和失败处理。
- 重放已有原生工具消息时，保留 assistant `tool_calls` 与 tool `tool_call_id` 的完整配对及顺序，不把工具轨迹拼成虚构的摘要或伪造新的工具返回。

现有工具循环在不同取证步之间压缩动作历史的做法不必整体改写。本批需要的是把“已经含有正文的准备请求”延续到最终阶段，不建立通用会话存储、跨请求缓存或第二套历史管理框架。

### 3.3 原文优先，准备结果提供要点

最终规则应从“只能依据准备事实和短 quote”调整为：

- 根据原问题组织回答，以历史中实际提供的原文为论文事实依据；准备事实帮助组织要点、关系和缺口，不作为不可修正的结论。
- 原文中存在、但准备遗漏的必要公式、条件、替代来源和限定，可以直接用于回答，并引用对应实际可见的 chunk。
- 准备事实与原文不一致时，以原文为依据；原文符号仍不清楚时保留局部不确定性，不根据常识补成确定关系。
- quote 继续使用现有字段和简短原句规则，但它不是完整正文的替代物。仅把 quote 限长调大不构成本批修复。
- 用户要求分析时，区分原文前提与推论。此前的模型回答、临时事实和工具状态不能自动成为已核实论文证据。

准备阶段的原子化、并列分支、模态与原问覆盖规则保留。不引入新的事实 schema、公式专用字段或语义审核动作。

### 3.4 最终引用与原文窗口保持一致

最终使用该次成功准备实际可见的完整 context，不再按 `facts.citation_ids` 二次筛选。最终 `allowed_citation_ids`、交给 `publish/validate_citations` 的 context，以及来源范围限定，应对应同一批正文。

允许引用“已提供正文、但准备事实没有引用”的块。候选位置、未展示块、parent ID 和其他版本仍不因为出现在历史中就获得引用资格。沿用原有来源和引用检查，不新增 quote 匹配器或支持度评分器。

固定证据入口相应取消“最终只能引用准备事实 ID”的额外限制，改为沿用该固定原文窗口的权限，继续走现有引用处理。

### 3.5 上下文与成本边界

8192 token 是现有原文证据窗口的预算，不是包含系统提示、工具历史、准备响应和输出要求在内的整个请求上限。本批不把重放历史描述成不消耗上下文，也不声称整个最终请求小于 8192 token。

只延续一次成功准备请求中实际发送的消息，不拼接每个旧请求保存的完整副本；同一批正文不同时出现在历史和最终事实包两处。维持原证据预算、模型、输出上限和 `ChatBudget`，不扩大窗口、不新增真实请求前的模型压缩或判别过滤。

正常仍是一次准备、一次最终生成；新增的是最终请求的原文输入 token。通过原有账本记录实际请求、token、耗时与重试／修复。若实际调用遇到上下文或输出限制，保留具体阶段失败，本批不靠静默截断公式、删条件或反复试跑掩盖它。

### 5.3 评价内容与成本

先从实际最终请求确认完整原文是否到达，包括未被 quote 覆盖的公式、句式、条件与限定；再对照最终完整回答，区分“传递修复”与“回答正确使用”。消息中有原文只证明可见，不自动证明模型正确使用。

评价围绕原问：知识来源与替代路径、词对筛选条件、硬编码关系和规则的说明是否有据；公式／关系一旦输出，其方向、符号、条件与归属是否忠实。原问未要求完整关系清单，未输出的链只记为未覆盖，不据此补题或认定传递失败。允许忠实的同义与 Unicode／LaTeX 等价表达，不根据单个关键词判质量。

允许模型从实际原文补足准备遗漏，引用权限正常通过不等于内容已经审核。评价为 AI 辅助原文对照，不称独立人工准确率；不运行 `direct_answer`／Answer F1／Evidence F1 比较，也不增加评委模型。
