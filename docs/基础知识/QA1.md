## 一、LLM 基础

### 1. 温度和 top-p 的区别？

**回答答案**

温度和 top-p 都是控制生成随机性的采样参数，但作用方式不同。

温度是在 softmax 之前缩放 logits：`p_i = exp(z_i / T) / Σ exp(z_j / T)`。温度小于 1 时分布更尖锐，模型更倾向高概率 token；温度大于 1 时分布更平，输出更随机；温度趋近 0 时接近贪心解码。

top-p 也叫 nucleus sampling：先把候选按概率从高到低排序，保留累计概率达到 p 的最小集合，再在这个集合里采样。p 越小，候选越少，输出越保守；p=1 相当于不按概率截断。

实际使用时，两者会叠加。Agent 场景通常用较低温度，保证工具参数、JSON 和引用 ID 稳定；创意写作才需要更高温度。不要同时大幅调低 top-p 和温度，否则输出会过于单一。

**解析**

- 温度和 top-p 不是“二选一”。常见做法是固定一个、微调另一个；很多 API 默认 top-p=1，只调温度。
- 温度 0 也不保证完全可复现：浮点运算、批处理、硬件和推理框架都可能带来差异。评测时要接受这种方差，或固定 seed、记录模型版本。
- top-k 是固定保留前 k 个候选；top-p 是动态集合。长尾分布下 top-p 更灵活。
- Agent 的低温度不是越低越好：太低会降低探索能力，遇到工具失败时不容易换策略；通常 0–0.3 是常见区间，具体看任务。
- 可追问：“为什么 JSON 输出还会失败？”因为温度只影响采样，不保证结构；还需要 schema 校验、JSON mode 或 function calling。

### 2. KV cache、prefill 和 decode 是什么？

**回答答案**

大模型是自回归生成：每生成一个 token，都要让当前 token 关注之前所有 token。Transformer 的每一层都会计算 Key 和 Value，如果每一步都重算历史 token 的 K/V，代价会非常高。KV cache 就是把历史 token 在每层的 K/V 缓存下来，生成新 token 时只计算新 token 的 Q/K/V，然后直接复用缓存。

一次推理通常分两个阶段。prefill 阶段把整段 prompt 并行送进模型，计算出所有输入 token 的 KV cache，并产出第一个 token；decode 阶段每次只生成一个 token，把新 token 的 K/V 追加到 cache，再继续下一步。

所以 prefill 决定首 token 延迟（TTFT），decode 决定后续每个 token 的延迟（TPOT）。KV cache 用显存换时间；上下文越长、并发越高，cache 占用越大。vLLM 的 PagedAttention 就是用分页管理 KV cache，减少显存碎片，提高吞吐。

**解析**

- KV cache 的显存近似为：`2 × 层数 × KV 头数 × head_dim × 序列长度 × batch × 字节数`。GQA/MQA 通过减少 KV 头数来降低 cache。
- decode 阶段通常是 memory-bandwidth bound，不是算力 bound；所以 batching 和量化对吞吐很关键。
- prefix caching 可以复用相同前缀的 KV；多轮对话里系统提示相同，就有复用空间。
- KV cache 不等于上下文窗口。上下文窗口是模型能处理的最大 token 数；KV cache 是实际占用的运行时显存。
- 可追问：“长上下文为什么贵？”因为 attention 计算和 KV cache 都随长度增长，且中间信息容易被稀释。

### 3. embedding 模型怎么选？要不要归一化？

**回答答案**

选 embedding 模型主要看五件事：语言和领域是否匹配、最大输入长度、向量维度、推理成本和检索评测效果。不要只看榜单，最好用自己业务的 query-doc 对做 recall@k、MRR 或 nDCG 评测。

查询侧和文档侧必须使用同一个模型、同一套预处理。很多模型有 instruction prefix，比如查询前加“query:”、文档前加“passage:”，用错会明显掉点。

要不要归一化取决于相似度算法。用 cosine 时，向量通常先 L2 归一化，这样内积就等于 cosine；用内积检索时，归一化可以避免长向量占优。维度也不是越高越好：高维更贵，低维可能够用；Matryoshka embedding 还支持截断维度。

**解析**

- bi-encoder 是 query 和 doc 分别编码，速度快，适合大规模召回；cross-encoder 是拼在一起编码，精度高但慢，适合 rerank。
- 领域不匹配时，可以用对比学习做微调，构造正例和 hard negatives；但要有评测集，不能只看 loss。
- 中文、英文、代码、公式的 tokenization 差异很大；论文场景还要考虑公式和术语。
- cosine 和 dot product 在归一化后等价；如果索引里混用归一化和未归一化向量，分数会不可比。
- 可追问：“embedding 维度越高越好吗？”不一定，取决于数据量、模型训练方式和检索成本；先测再定。

### 4. RAG 和 fine-tuning 怎么选？

**回答答案**

RAG 和 fine-tuning 解决的不是同一个问题。RAG 把外部知识放在索引里，回答时检索出来，优点是知识可更新、可溯源、可引用，适合论文、文档、企业知识库这类经常变化且需要出处的场景。fine-tuning 是改模型权重，更适合改变行为、格式、语气、领域表达或分类能力，不适合可靠地注入事实。

如果知识频繁变化、需要引用、需要权限隔离，优先 RAG；如果只是想让模型稳定按某个 JSON 格式输出、模仿某种风格、提升领域术语理解，可以考虑 fine-tuning；如果两者都需要，常见组合是 RAG 提供事实，轻量微调优化格式和表达。

还要算成本和风险：RAG 增加检索延迟和索引维护；fine-tuning 需要高质量数据、训练资源，还会有灾难性遗忘和版本管理问题。很多场景其实 prompt engineering + 工具调用就够了，不必上微调。

**解析**

- fine-tuning 注入事实不可靠：模型可能记住训练集，也可能在新问题上编造；而且知识更新要重新训练。
- RAG 的失败点通常在召回、重排、上下文选择和引用，不是“模型不够大”。
- LoRA/QLoRA 只训练低秩适配器，成本低，适合风格和格式适配；全量微调成本高。
- 微调后仍需要 schema 校验和评测，不能假设输出一定合法。
- 可追问：“能不能用 fine-tuning 替代 RAG？”可以替代一部分，但可溯源、实时更新和权限控制会变差；大多数知识问答仍建议 RAG。

## 二、RAG

### 5. chunk size 和 overlap 怎么定？

**回答答案**

chunk 大小没有统一最优值，要按文档结构、语义完整性和 token 预算来定。常见起点是 200–800 token，overlap 10%–20%，然后用自己的评测集调。技术文档、论文、合同的结构不同，不能直接套一个数字。

更稳的做法是结构感知分块：按标题、段落、列表、表格切，尽量保证一个 chunk 是一个完整语义单元；再用父子块兼顾检索粒度和上下文完整性——子块用于向量检索，命中后展开父块给模型。overlap 主要解决边界信息被切断的问题，但会增加索引体积和重复内容。

最终判断标准不是 chunk 看起来整齐，而是召回率、答案质量和引用是否准确。

**解析**

- chunk 太小：语义不完整、召回噪声多、需要更多 top-k；chunk 太大：embedding 被无关内容稀释、上下文预算浪费。
- overlap 不是越大越好；重复内容会挤占 top-k，也会让引用去重变复杂。
- 论文里的公式、表格、图注最好单独处理，不要和正文硬切在一起。
- 父子块、句子窗口、语义分块都是常见方案；选择取决于查询类型和评测结果。
- 可追问：“中文怎么切？”按标点和段落切只是起点，还要看术语、公式和标题层级；不要只按固定字符数。

### 6. 向量检索和 BM25 各自优劣？为什么用 RRF？

**回答答案**

向量检索是稠密检索，擅长语义相似和同义表达，比如用户问“怎么减少幻觉”，文档写“提升事实一致性”，向量可能召回；但它对精确 ID、数字、稀有术语、专有名词不一定敏感。

BM25 是稀疏检索，基于词频和逆文档频率，擅长精确词匹配，尤其是人名、模型名、公式编号、错误码；但它不懂同义词和语义改写，分词和语言差异也会影响效果。

所以常见做法是混合召回：两路各取 top-N，再用 RRF 融合。RRF 的分数是 `Σ 1/(k + rank)`，只看排名，不看原始分数，因为向量相似度和 BM25 分数的量纲不可比。k 通常取 60 左右，起到平滑作用。融合后再接 rerank，精度会更好。

**解析**

- RRF 的优点是简单、无需训练、对不同检索器鲁棒；缺点是完全忽略分数差距，如果一路明显更可靠，可以给加权 RRF。
- 候选深度很重要：两路各取 20–100 条，再融合；只取 top-5 融合，收益有限。
- BM25 对中文需要合适的分词；英文还要考虑词干化、停用词。
- 向量检索的领域外泛化、长文档、跨语言是优势；精确匹配是弱项。
- 可追问：“RRF 和加权分数融合怎么选？”没有标注时 RRF 更稳；有评测数据时可以学习权重或做归一化。

### 7. rerank 的作用和成本？什么时候不上？

**回答答案**

rerank 通常用 cross-encoder：把 query 和 doc 拼在一起送进模型，让模型直接判断相关性。它比 bi-encoder 的向量相似度更准，因为它能看到 query 和 doc 的交互信息。

典型链路是：召回 top-50 到 top-200，rerank 后取 top-5 到 top-20 给生成模型。成本主要是延迟和费用：每个候选都要跑一次模型，候选越多越慢；GPU 批处理可以缓解，但仍然比向量检索贵。

什么时候不上？召回质量已经很好、延迟预算很紧、候选数量很大、或者 rerank 模型和领域不匹配时，可以先用 RRF 或轻量排序。rerank 也不能救回没有召回的文档，所以召回是前提。

**解析**

- bi-encoder 是“先编码再比较”，cross-encoder 是“联合编码”，精度高但无法预计算。
- 还有 late interaction（如 ColBERT），介于两者之间，用 token 级匹配兼顾精度和成本。
- rerank 的 top-k 要跟上下文预算匹配；rerank 50 条但最终只能放 5 条，要确保截断策略合理。
- 评测看 nDCG@k、recall@k、MRR，以及最终答案和引用质量。
- 可追问：“rerank 一定提升吗？”不一定；如果召回里没有正确文档，或者 rerank 模型域外，可能反而变差。

### 8. 召回有结果但答案错，怎么分层定位？

**回答答案**

不要直接改 prompt，先把链路拆开看：

1. 召回：正确证据有没有进入候选集？看 recall@k、候选 ID。
2. rerank：正确证据有没有被排到后面或排丢？看排序前后位置。
3. 上下文选择：有没有被去重、截断、预算排除，或者被无关内容挤掉？
4. 生成：模型有没有忽略、误读、夸大，或者把模型知识当成论文证据？
5. 引用：引用是否真的支持结论？有没有引错 chunk？

最有效的方法是做反事实实验：把 gold context 直接喂给模型。如果答对了，问题在检索或上下文选择；如果还错，问题在生成、提示或模型能力。再结合 trace 看每一步的输入输出，不要只看最终答案。

**解析**

- 常见问题包括“lost in the middle”：关键证据在长上下文中间被忽略；可以调整排序、把关键证据放前面、减少无关上下文。
- 上下文冲突：多个 chunk 说法不一致，模型可能选错；需要来源优先级或冲突提示。
- 引用错位：答案对但引用错，属于 attribution 问题，不是生成问题。
- 分阶段指标比一个总分更有诊断价值：recall、nDCG、context precision、faithfulness、answer correctness。
- 可追问：“怎么判断是模型知识还是论文证据？”看引用和 claim 的 basis；要求模型区分 paper_evidence 和 model_knowledge，并做引用校验。

## 三、Agent

### 9. ReAct 是什么？和 Plan-and-Execute 的区别？

**回答答案**

ReAct 是一种 Agent 策略：模型交替进行推理（Reason）和行动（Act），每次行动后观察环境返回（Observation），再决定下一步。它没有强制的全局计划，适合路径不确定、需要边做边调整的任务。

Plan-and-Execute 是先让模型生成一个计划，再按步骤执行；执行器可以并行、可以人工审核，计划也可以在执行中修订。它的优点是可控、可审计、延迟可能更低；缺点是计划错了他会一路错下去，需要 replan。

实际系统经常混合：先做粗粒度计划，再用 ReAct 根据观察修正；或者用 ReWOO 把推理和观察分开，减少重复 token。选择取决于任务确定性、工具成本和可接受的失败模式。

**解析**

- ReAct 不是某个框架的专利，本质是“工具调用 + 观察回填”的循环；function calling 是它的实现机制之一。
- ReAct 容易循环、步数多、成本高；需要最大步数、重复检测和终止条件。
- Plan-and-Execute 的计划质量依赖模型对任务的分解能力；计划太长会失真，太短又不够。
- 可追问：“ReAct 一定比 Plan 好吗？”不一定；确定性任务用 Plan 或 workflow 更稳，开放探索才需要 ReAct。

### 10. Agent 和 workflow 的区别？什么时候不用 Agent？

**回答答案**

workflow 是预先设计好的固定路径，比如“先检索，再重排，再生成，再校验”；每一步、分支和失败处理都是人写死的。Agent 则把“下一步做什么”交给模型，根据当前观察动态选择工具和参数。

workflow 的优点是稳定、可测试、成本低、可审计；缺点是覆盖不了开放式情况。Agent 的优点是灵活、能处理未知路径；缺点是延迟和成本高、行为不确定、评测和调试更难。

所以确定性任务优先 workflow；只有路径真的无法预先枚举、需要动态选工具或动态分解任务时，才用 Agent。很多生产系统其实是“workflow 骨架 + Agent 子步骤”的混合，而不是全自主 Agent。

**解析**

- 面试里不要把所有 LLM 应用都叫 Agent；有工具调用不等于有自主决策。
- Agent 的“自主”是有限度的：工具集合、权限、预算、终止条件都是人设计的。
- workflow 更容易做幂等、重试、人工审核和合规；Agent 需要额外的 guardrail。
- 可追问：“怎么判断要不要 Agent？”看任务路径是否可预定义、失败成本、延迟要求和可观测性要求。

### 11. 如何防止 Agent 死循环或跑飞？

**回答答案**

要从系统层面防，不是只靠提示词。常见手段：

- 最大步数、最大工具调用次数、最大 token 和时间预算；
- 重复查询检测：对 query + 版本范围做规范化，相同或高度相似就返回 duplicate，不再检索；
- 无新证据停止：如果一轮检索没有新增可展示证据，就禁止继续无意义重试；
- 明确的状态机：允许的动作随阶段变化，最终阶段只允许 answer；
- 记录每次 observation 和剩余预算，让模型知道还能做什么；
- 明确的终止状态：answered、insufficient、needs_clarification、error。

这些条件要写成代码约束，模型只能在约束内决策。触顶后可以做一次“基于现有证据的收尾”，而不是无限续步。

**解析**

- 重复检测不能只做字符串相等；要规范化空格、大小写，必要时做语义相似度。
- “没有新证据”比“没有调用工具”更可靠；模型可能换一个 query 但拿到同样的 chunk。
- 反思/自我批评也可能导致循环；要限制 reflection 次数。
- 工具错误重试要有上限和退避，不能把网络错误当成“再想想”。
- 可追问：“5 步怎么定？”这是工程参数，要看平均步数、触顶比例和收益；没有理论最优。

### 12. 工具失败、超时、返回脏数据怎么处理？

**回答答案**

把工具失败当成一种正常的 observation 返回给模型，而不是抛异常吞掉。错误信息至少包含：错误码、可读消息、是否可重试、已经产生什么副作用。

处理策略：

- 瞬时错误（超时、429、5xx）：有限次重试 + 指数退避 + 抖动；
- 参数错误：把校验信息返回给模型，让它修正参数，而不是盲目重试；
- 工具不可用：切换备用工具或降级；
- 需要用户输入：暂停并提问；
- 无法继续：保留已有证据，带缺口停止，不要伪造成功。

有副作用的工具还要考虑幂等键、事务、补偿操作和人工审批。模型可能“以为成功”，所以程序要校验返回结果，不能只相信模型的复述。

**解析**

- 工具错误信息也是 prompt 的一部分；写得越可操作，模型越容易恢复。
- 重试要有上限，避免放大故障；区分 retryable 和 non-retryable。
- 超时时间要小于上游请求的超时，避免级联阻塞。
- 脏数据要校验 schema、类型、范围和来源；不要让模型直接消费未验证的原始输出。
- 可追问：“工具已经执行成功但响应丢了怎么办？”用幂等键查询状态，或让工具支持“查询执行结果”，避免重复副作用。

### 13. 如何设计一个好工具？

**回答答案**

工具是给模型用的 API，设计重点和给人用的 API 不完全一样。一个好的工具应该：

- 名字和描述清楚，说明什么时候用、什么时候不要用；
- 参数用严格的 JSON Schema，字段少而明确，枚举和必填项齐全；
- 一个工具只做一件事，避免功能重叠导致模型选错；
- 错误可读、可操作，返回结构稳定；
- 有超时、限流、权限控制和幂等设计；
- 返回结果带 ID、来源和必要元数据，方便后续引用；
- 输出不要过大，必要时分页或摘要。

工具描述本身就是 prompt，应该像写文档一样测试：给模型几个典型任务，看它是否能选对工具、填对参数。

**解析**

- 工具太多会增加选择困难；可以分层、分组或按阶段暴露。
- 参数越自由，模型越容易填错；能用枚举就不要用自由文本。
- 返回值要区分“事实”和“建议”，避免模型把工具的解释当数据。
- 有副作用的工具要加确认、沙箱和审计；读工具和写工具权限分开。
- 可追问：“function calling 和 MCP 的关系？”function calling 是模型调用工具的机制；MCP 是工具提供方和 Agent 之间的标准化协议，解决集成和复用。

---

### 14. 多 Agent 一定更好吗？MCP 解决什么？

**回答答案**

不一定。多 Agent 的收益主要来自分工、并行和专业化，但代价是协调开销、上下文重复、错误传播、延迟和成本上升。很多任务单 Agent 加几个好工具就够了。

适合多 Agent 的情况：子任务可以独立并行、需要不同角色/工具/权限、单个上下文放不下、需要交叉验证。常见模式是 supervisor 负责分派，worker 执行，最后汇总；或者 handoff 把控制权交给更合适的 Agent。

MCP 解决的是另一个问题：它标准化了 Agent 和工具/资源提供方之间的接口，让工具可以复用、替换和独立部署。MCP 不是多 Agent 框架，也不自动解决权限和调度问题。

**解析**

- 多 Agent 的失败模式：互相甩锅、重复劳动、共享状态不一致、消息丢失、成本失控。
- 先证明单 Agent 不够，再拆多 Agent；拆分后要有明确的通信协议和终止条件。
- MCP 基于 client-server，通常用 JSON-RPC；工具、资源、prompt 都可以暴露。
- MCP 的安全边界很重要：远程工具可能带来数据泄露和权限提升。
- 可追问：“多 Agent 怎么评估？”除了最终任务成功率，还要看通信次数、重复工具调用、总 token 和延迟。

## 四、评估与工程

### 15. 如何评估一个 Agent？

**回答答案**

Agent 评估要分层，不能只看最终答案。

- 组件层：检索 recall@k、rerank nDCG、工具选择准确率、参数正确率；
- 轨迹层：步数、无效调用、重复调用、错误恢复率、是否按预期使用工具；
- 端到端层：任务成功率、答案正确性、证据忠实度、引用准确率；
- 运行层：token 成本、延迟、失败率、超时率、安全事件。

离线用固定题集和 gold 轨迹，在线用抽样、用户反馈和 A/B。Agent 是多轮系统，评估要同时看最终状态和过程；只看最终答案会掩盖“碰巧答对但过程不可靠”的问题。

还要注意样本量和置信区间，不要用 5 道题得出“准确率提升”的结论。

**解析**

- 任务成功率和答案质量不是一回事：答案可能对，但工具调用错、引用错、成本高。
- LLM-as-judge 可以做粗筛，但要有 rubric、人工校准和抽检。
- 评测集要覆盖：正常路径、工具失败、无答案、歧义、多轮、越权、长上下文。
- 防止过拟合：保留 holdout，不根据测试集反复调 prompt。
- 可追问：“没有 gold 轨迹怎么办？”用人工标注少量、规则检查、LLM judge + 人工抽检，先建立可重复的基线。

---

### 16. LLM-as-judge 有什么坑？

**回答答案**

LLM-as-judge 是用一个模型给另一个模型的输出打分。它便宜、可扩展，但有几个典型问题：

- 位置偏差：pairwise 比较时偏好第一个或第二个；
- 长度/格式偏差：偏好更长、更工整、更“像答案”的输出；
- 自我偏好：同一家模型可能偏爱自己的风格；
- 提示敏感：rubric 稍微改一下，分数就变；
- 与人工相关性不稳定：不同任务、不同模型差异很大；
- 成本：大规模评估并不便宜；还有数据泄露风险。

缓解办法：写清楚 rubric、提供参考答案、pairwise 交换顺序、多 judge 投票、固定温度和模型版本、用人工标注集校准。它适合粗筛和回归，不适合作为高风险场景的唯一验收标准。

**解析**

- 绝对打分比 pairwise 更难校准；能用 pairwise 就少用 1–10 分。
- judge 也会被 prompt injection 或答案中的指令影响；要隔离待评内容。
- 报告时要给出 judge 模型、版本、提示、温度和抽样方式，否则结果不可复现。
- 可追问：“怎么验证 judge 可信？”拿一部分人工标注算相关性/一致率，定期复检。

---

### 17. 长任务怎么设计？FastAPI 同步接口有什么问题？

**回答答案**

Agent 任务可能跑几十秒甚至几分钟，不能用一个同步 HTTP 请求硬扛。同步接口的问题是：容易触发网关超时、长期占用 worker、客户端断开后任务状态丢失、无法查询进度、重试可能重复执行。

更稳的设计是 job 模式：

1. `POST /tasks` 创建任务，立即返回 `job_id`；
2. 后台 worker 从队列取任务执行；
3. 任务状态和结果存 Redis/Postgres/对象存储；
4. 客户端用 `GET /tasks/{id}` 轮询，或通过 SSE/WebSocket 接收进度；
5. 支持取消、超时、重试、死信队列和幂等键。

FastAPI 里不要把阻塞调用直接放在 async 函数里，否则会卡事件循环；CPU/阻塞 IO 可以放线程池，重任务交给独立 worker。

**解析**

- SSE 是单向服务器推送，简单、兼容性好；WebSocket 是双向，适合交互式取消/确认。
- 多 worker 部署时，进程内 Future/dict 不能共享状态；必须用外部状态存储。
- 本地 Qdrant 这类单进程资源，会限制多 worker 并发；生产要考虑 server 模式。
- 幂等键防止用户重复点击导致重复计费/重复副作用。
- 可追问：“任务执行到一半服务重启怎么办？”持久化状态、可恢复的步骤、幂等重放；不能恢复的要明确失败。

---

### 18. 如何做可观测性和故障回放？

**回答答案**

Agent 的可观测性要能回答三个问题：它做了什么、为什么这么做、失败在哪一步。

每个 run 记录：

- run id、session id、用户输入、模型和提示版本；
- 每次 LLM 调用的 prompt、输出、token、延迟；
- 每次工具调用的参数、返回、错误、耗时；
- 检索的 query、候选 ID、分数、最终上下文；
- 预算、步数、终止原因、重试/修复记录。

这些数据要能串成 trace，最好支持按 run 回放。指标上关注成功率、平均步数、工具错误率、token/成本、P95 延迟、超时率。日志要注意脱敏，不能记录密钥和敏感数据。

**解析**

- OpenTelemetry 适合通用 trace；LangSmith/Langfuse/Phoenix 更偏 LLM 应用。
- 回放不是简单重跑：模型版本、温度、工具状态都可能变；要记录配置和输入快照。
- 失败归因：模型能力、提示、工具、检索、数据、预算，分开统计。
- 线上采样和离线全量结合；全量记录成本高，关键路径可以全采。
- 可追问：“怎么定位一次答错？”先看 trace 中哪一步偏离预期，再用反事实实验验证。

## 五、安全与系统设计

### 19. 如何防 prompt injection 和工具滥用？

**回答答案**

先建立威胁模型：攻击者可能通过用户输入、检索到的文档、网页、工具返回，注入指令，让 Agent 越权、泄露数据或执行危险操作。间接注入尤其危险，因为恶意内容藏在“资料”里。

防御要分层：

- 指令与数据分离：明确告诉模型哪些是数据，不要执行数据里的指令；
- 最小权限：工具只给完成任务必需的权限，读和写分开；
- 工具 allowlist 和参数校验：不让模型自由构造危险参数；
- 沙箱：代码执行、文件访问、网络访问都在隔离环境；
- 人工审批：删除、支付、发邮件、执行命令等高风险操作二次确认；
- 输出校验和出站控制：防止把密钥、隐私数据带出去；
- 审计和告警：记录敏感工具调用，异常行为可追溯。

不能只靠“忽略之前的指令”这类提示词；真正的安全边界在能力限制和权限控制。

**解析**

- 直接注入 vs 间接注入：后者通过 RAG 文档、网页、工具输出进入上下文，更隐蔽。
- 双 LLM 模式：一个模型处理不可信内容，另一个有权限的模型做决策；能降低但不能消除风险。
- MCP 远程工具会扩大攻击面，要校验来源、权限和返回内容。
- 红队测试：构造恶意文档、越权请求、数据外泄场景，定期演练。
- 可追问：“提示词防御够吗？”不够，提示词只是纵深防御的一层，必须有系统级权限和沙箱。

### 20. 设计一个 code agent / research agent，你会怎么拆？

**回答答案**

先明确目标、用户、边界和失败成本，再拆组件。

以 code agent 为例：

- 工具：读文件、搜索、写文件、执行命令、跑测试、查看 diff；
- 环境：容器沙箱、资源限制、网络白名单、文件系统隔离；
- 状态：任务目标、计划、已修改文件、测试结果、错误日志；
- 循环：计划 → 修改 → 执行/测试 → 观察 → 修正；设最大步数和预算；
- 权限：破坏性操作要审批，敏感仓库要隔离；
- 评估：测试通过率、diff 质量、回归失败、成本、延迟；
- 可观测性：每步命令、输出、diff、token 和错误。

research agent 则把工具换成搜索、读论文、引用管理；重点是证据注册、来源质量、引用校验和不确定性表达，而不是代码执行。

无论哪种，先从 workflow + 少量工具开始，证明需要自主决策后再加 Agent 循环；不要一上来就多 Agent。

**解析**

- code agent 的核心风险是“能执行命令”；沙箱和权限比提示词重要。
- research agent 的核心风险是“编造来源”；要有 evidence registry 和 citation validation。
- 计划粒度：太细会僵化，太粗会失控；可以分层计划。
- 人机协同：关键节点暂停确认，比全自动更可靠。
- 可追问：“怎么评估 code agent？”除了最终测试，还要看是否引入回归、是否改错文件、是否执行危险命令、成本多少。
